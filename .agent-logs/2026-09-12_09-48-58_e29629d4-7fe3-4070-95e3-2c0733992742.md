## Must fix (correctness)

1. **Empty price inputs parse as `0`.** The GET form submits `minPrice=&amp;maxPrice=` when boxes are blank, and `Number("")` is `0`. `parseCatalogQuery` must treat trimmed-empty as absent before numeric parsing, or every form submit silently adds a `$0` floor and every generated link carries `minPrice=0`. Add a test for it.

2. **Handle `string[]` values in `searchParams`.** Next 16 gives `{ [key]: string | string[] | undefined }` (`/s?category=a&amp;category=b` → array). Take the first element in one small `first()` helper; otherwise `CATEGORIES.some(c =&gt; c.slug === raw.category)` fails on arrays and strict TS will flag it anyway.

3. **Keep `lib/catalog.ts` free of runtime Prisma imports.** `SortDropdown` (client) will import `catalogHref` from it, so `lib/catalog.ts` ends up in the browser bundle. `import type { Prisma }` is fine, but any runtime use (`Prisma.SortOrder.asc`) would pull `@prisma/client` client-side and break the build. Use literal `"asc" | "desc"`. Simpler alternative that removes the risk entirely: compute `options: { value, label, href }[]` on the server and pass that to `SortDropdown` — the client component then only needs `useRouter`.

4. **Results bar placement.** The "1-24 of 194 results" text depends on `total`, which only exists inside `CatalogResults`. Either render the whole results bar (count + `SortDropdown`) inside `CatalogResults`, with the skeleton fallback reserving that row, or put only the count inside. The plan currently puts the bar in the shell and the count in the child, which is two rows and contradicts the sketch.

5. **Key the Suspense boundary.** Client navigations (`router.push`, `&lt;Link&gt;`) are transitions, so an already-revealed Suspense boundary keeps the old grid until Neon answers — no feedback when changing sort/filter. `&lt;Suspense key={JSON.stringify(query)} fallback={...}&gt;` forces the skeleton per query. One line.
